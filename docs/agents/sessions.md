# Sessions and their trust boundaries

What each Managed Agents session of this repo can do. Read it before you add a session kind, or before you change the token, the agent or the environment of one.

A GitHub Actions job starts every session. The job holds the API key `JUDGE_ANTHROPIC_API_KEY` and its own token, `github.token`. No session holds either one. The job reads each answer, decides in code, and writes to GitHub with its own token. The job of `factory.yml` also holds `FACTORY_SELF_TOKEN` and the private key of the App `dsf-builder`. No session holds either one. The job of `repair.yml` also holds that private key. Its build step mints an installation token of the App, with `contents: write` and `workflows: write`, for the ref calls of `build.py` on the branch `repair-base/<n>` alone, because `github.token` holds no `workflows` permission (#403). Every other call of that step uses `github.token`. No session holds the App token.

The reader, the judge angles and the synthesis run on the judge's agent and the judge's environment. Their files are `.github/agents/judge.md` and `.github/agents/judge.environment.yaml`. The agent turns on the `agent_toolset_20260401` tools, with `web_fetch` and `web_search` off. The environment has the networking type `limited`, `allow_package_managers` true, and an empty `allowed_hosts`.

The factory's sessions run on the agent `dsf-builder` and the environment `dsf-builder`. Their files are `.github/agents/builder.md` and `.github/agents/builder.environment.yaml`, and `factory.yml` reads their ids from `claude-lock.json`. The agent has the same tools as the judge's agent. The environment has the networking type `limited`, `allow_package_managers` true, no packages, and the `allowed_hosts` `builds.dotnet.microsoft.com`, `dotnet.microsoft.com`, `api.nuget.org` and `globalcdn.nuget.org`. The session installs the SDK with `dotnet-install.sh` into `/root/.dotnet`. These sessions run when the factory runs with `--agent managed`, as `factory.yml` does since #379. With the default `--agent claude-code`, the agent phases run in a Docker sandbox on the runner, and no session starts. On both paths the gates run in a Docker container.

A story that edits `.github/workflows/` needs the App permission `workflows: write`. Grant it in the settings of the App `dsf-builder`. Without it, GitHub refuses the push of a change to a workflow file.

The condition of that grant is the path rule of `.github/repair/merge.py`, decided in #406. The merge step of `repair.yml` merges no `repair` pull request whose diff touches a file under `.github/workflows/` other than `factory.yml`, or `.github/judge/`, `.github/repair/` or `.claude/skills/change/JUDGES.md`. It also merges no diff of `factory.yml` that changes the block of its top-level `on:` key or of a `permissions:` key at any depth, or whose added or removed lines hold the token `permissions`, `on` as a key at column 0, a flow collection, a quoted scalar, an anchor, an alias, a tag or an explicit key. That check reads text and fails closed: a step edit that names `permissions` in a scalar, or that uses flow style, is refused and stays the owner's direct change. A changed line that opens a quoted scalar, balanced or not, or that holds a character outside printable ASCII, is refused too: an open quote can swallow the `permissions:` block into a scalar, and a byte order mark can hide `on:` from a match at column 0. The diff is read against the base of the pull request, so the step merges no pull request whose base is not the default branch, and it reads the base again directly before it arms the merge. A workflow on `pull_request` runs from the pull request's own copy, and a workflow with `checks: write` can post a green `judge-verdict`. `judge.py` reads `.github/judge/` and `JUDGES.md` as the rules of the judge. So a repair that edits them judges itself. The rule runs from `main`, and it is under `.github/repair/`, so a repair that edits the rule is refused by the rule. The rest of `factory.yml`, and `.github/agents/`, `src/` and `sandbox/`, stay open to a repair.

Read each value off the code and the files under `.github/agents/`. Change this table in the pull request that changes the code it reads.

Under `--agent managed`, the gates run the agent's code in a container of the image `sandbox/Dockerfile`, as the runner's user id. The container has its own pid namespace, no `sudo`, no docker socket, and no path of the runner other than the work tree and a new home directory. Its `docker run` carries neither `ANTHROPIC_API_KEY` nor `ANTHROPIC_BASE_URL`. `.factory` and `specs` are read-only in it, since the factory on the runner reads and writes them, and a link there would reach a file of the runner. `Sandbox.StartForGatesAsync` refuses a symbolic link at either path, since Docker would mount the directory of the runner that it names. `FeatureFiles.ReadScenarioTitles` refuses a symbolic link that a session commits, and its parse error holds positions and no text of the file. These two hold the boundary at `specs`, and the mount is a second layer: a pull that leaves no file under `specs` makes git remove the directory, which detaches the mount, and `specs` is then writable for the rest of the run. A tracked file under `.factory/` stops the run before each prompt and after each pull, since a session uploads what `.factory/` holds. So the agent's tests, MSBuild targets and `## Check` block cannot read a secret of the job. Only a name that the test gate passes reaches a command. The container has network access, and it can write the rest of the work tree and its home directory on the runner. A `## Check` block has the tools of the image: `git`, `dotnet`, `node`, `curl` and the base image tools, and no `python3`, `jq` or `gh`. The job's image build takes about 1 minute for each run. `AGENTS.md`, under `## Docker`, states why a pid namespace on the runner is no boundary.
